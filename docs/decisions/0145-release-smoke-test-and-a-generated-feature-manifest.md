# A release runs a smoke test and publishes a feature manifest per build

**Decision:** every release tag runs a smoke test on each build it can execute
and publishes a machine-readable feature manifest for each build, both as
release assets (#307).

## Why

v0.7.1's features (#303) are gated differently: Dreaming mode and the srt
sandbox are in every build, while speech output (`voice`) and RL Studio
(`train`) are not in the default-feature tarballs. A download gave no
machine-readable way to tell which build carried which, and nothing re-ran the
binary to confirm it even starts. The release notes could say it in prose, but
prose is not an artifact a script or a later tool can read, and prose is not a
test.

## The manifest is generated by the workflow, not read back from a binary

The feature set that matters spans crates: `voice`, `train`, `recall`,
`memory`, `search` and `research` live on `zorp-web`, not on `zorp-agent`, so
no single binary's `cfg!` can report the whole build's capabilities. The
workflow that builds an artifact knows the exact feature set for certain, because
it is what it passed after `--features` (empty for the tarballs, the full set
for the macOS DMG). So `scripts/feature-manifest.sh` takes that set and emits
stable, sorted JSON. The script's output shape is pinned by
`tests/feature_manifest.rs` on every pull request, because the script itself
only runs during a release and a check that runs only during a release is a
check nobody has run (the same reasoning as `check-release-version.sh`).

## The smoke test never fakes a model interaction

`scripts/release-smoke.sh` checks that the built `zorp-agent` reports the tag's
version, that `--help` runs, and that `zorp-web` answers `GET /api/health` with
a healthy body on loopback. A real model interaction needs a model endpoint,
which a release runner does not have, so that step runs only when the caller
sets `ZORP_SMOKE_PROVIDER=1` with a provider configured and is reported
**skipped** otherwise, never faked. A release smoke test that invented a model
reply would be the one result worth nothing. Wiring a provider (a scripted
loopback stub, or a free endpoint) into the release so the model step always
runs is a later decision; the hook is in place.

## Coverage, and what only runs on a tag

- Tarball builds (`release.yml`): per-target feature manifest (all targets,
  since it runs nothing) and the smoke test on every target whose runner can
  execute it: both Linux targets (x86_64 on ubuntu-22.04, aarch64 natively on
  ubuntu-22.04-arm), macOS arm64, and Windows. The one unsmoked target is
  x86_64-apple-darwin, which is cross-compiled on the arm64 macOS runner and
  cannot run there.
- DMG (`desktop.yml`): a feature manifest whose feature set is read from the
  bridge crate's own `default = [...]`, which is exactly what `build-bridge.sh`
  compiles (it passes no `--features`), so the manifest cannot drift from the
  build the way a hardcoded list would. A true headless GUI launch is
  impractical in CI; the existing mount-and-verify of the app bundle is the
  proxy.
- Image (`image.yml`): an **anonymous** pull of the published image, after
  logout, so a private package fails the check rather than passing on the
  job's own still-authenticated session.

These paths execute only on a real tag (or a `workflow_dispatch` rehearsal), so
the first release after this lands is where the end-to-end run is first
observed. The parts that can run on every pull request, the manifest script and
its test, do.
