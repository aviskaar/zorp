# co-write: draft an artifact from the run record, human is author of record

**Date:** 2026-08-09
**Status:** approved

## Purpose

The third of zorp's four capabilities. Given a track that has at least one
recorded metric, `co-write` drafts a markdown artifact grounded in the
track's actual evidence, evidence checkpointed by `validate` and metrics
recorded by `investigate`, and hands it to a human who becomes its author
of record. zorp never marks a draft "done" on its own; the checkpoint
here is a review gate on the draft's readiness for a human to take over,
not a publication decision. See
`docs/superpowers/specs/2026-08-09-zorp-architecture-design.md` for why
the human is always the author of record, and
`docs/superpowers/specs/2026-08-09-zorp-investigate-design.md` for the
sibling capability this one draws its metrics from.

## Where this lives

A new module in `zorp-agent`, `zorp-agent/src/co_write/mod.rs` (plus
`error.rs`; no `result.rs`, since the agent's final answer is taken
directly as the draft's content, not parsed as a scored JSON verdict),
exposed as a new subcommand, `zorp-agent co-write "<question>"`, behind
the existing `research` feature. It reuses:

- `zorp_track::Project` and the existing `Agent`/`attach_mcp_tools`
  wiring, built the same way `validate` and `investigate` build their
  agents.
- `Store::get_validation(track_id)` for validate's verdict, scores, and
  citations, if a validation exists. This returns
  `Result<Validation, TrackError>`, erroring `TrackError::NotFound {
  kind: "validation", .. }` when none exists; `co_write::run` treats that
  specific error as "no validation yet" (`None`), not a failure, matching
  the existing "four standalone capabilities" decision, validate is
  optional.
- `Store::experiments_for(track_id)` (added while building `investigate`)
  and `Store::metrics_for(experiment_id)` (already built), concatenated
  across every experiment the track has, to assemble the full set of
  recorded metrics available to draft from.

## Grounding the draft, not checking it afterward

The task prompt hands the agent the track's evidence as structured data:
the hypothesis, validate's verdict/scores/citations if present, and every
`(metric_key, MetricValue)` pair recorded across all the track's
experiments, each metric's originating experiment id included so the
agent can distinguish separate attempts. The system prompt states the
discipline plainly: cite only the metric values given, do not invent
numbers, do not state confidence beyond what the evidence supports.

This is a deliberately lighter mechanism than validate's or investigate's
citation-required parsing: there is no post-hoc pass that scans the
drafted prose for numeric claims and re-verifies each against the
metrics table. That's a substantially harder problem (extracting a
number from free-form prose and matching it back to a specific metric
row is its own source of false positives and negatives), and the
grounding happens at the input side instead, the agent is handed only
real numbers to work with in the first place, not a superset it must be
checked against afterward. Revisit if drafts are observed citing
numbers not in the provided set despite the prompt's instruction.

## Gate: at least one metric must exist

`co_write::run` refuses with `CoWriteError::NoMetrics` if the track has
zero recorded metrics across all its experiments. A validate pass alone
(redundancy/feasibility scores, no investigate attempt ever run) isn't
enough to draft from: that scoring is the go/no-go check that already
happened, not evidence the artifact should present. This is checked
before the agent is built, so a track with nothing to draft from fails
immediately and clearly.

## Producing the draft

Unlike `validate` and `investigate`, `co_write::run`'s task prompt does
not ask for a fenced JSON block. The agent's `Outcome::Complete(text)` is
taken directly as the draft's full content and written to
`project.track_dir(track_id).join("draft.md")` via `fs::write`, prose in,
prose out; this is a document, not a scored verdict.

Before overwriting an existing `draft.md`, `co_write::run` checks whether
the file's current mtime is later than co-write's own last checkpoint
for this track. This needs one small new `zorp-track` function,
`Store::latest_checkpoint_time(track_id, kind) -> Result<Option<i64>,
TrackError>`, reading the `resolved_at` of the most recent checkpoint row
matching `kind` (`checkpoints` already has `created_at`/`resolved_at`
columns; `record_checkpoint` sets `resolved_at` to the same timestamp as
`created_at` since the decision is made synchronously, so either column
works for this comparison). If the file's mtime is later than that
timestamp, `co_write::run` prints a warning to stderr, "draft.md appears
to have been edited since it was last generated by co-write", and then
overwrites anyway. This is a heuristic warning, not a tamper-evidence
hash like `prereg.md`'s: it does not block the overwrite, and a track
with no prior co-write checkpoint (first call) never triggers it.

## Checkpoint

After writing `draft.md`, `co_write::run` calls
`Store::record_checkpoint(track_id, "co-write", checkpoint_mode,
prompt)`, where `prompt` shows the draft's file path, its line count, and
how many metrics it drew on. Unlike `validate` and `investigate`,
**rejecting this checkpoint does not kill the track.** A draft not being
ready is not evidence the underlying investigation failed: the human can
simply call `co-write` again, or take `draft.md` and edit it by hand from
here, which is the expected normal path once a draft exists at all.
`co_write::run` returns `Result<bool, CoWriteError>`, the same
approved/rejected shape as its siblings, but with no
`Store::set_track_status` call on either branch.

## Error handling

- Track status is `Killed`: `CoWriteError::TrackKilled`, checked before
  anything else (same posture as `investigate`).
- Zero recorded metrics across all the track's experiments:
  `CoWriteError::NoMetrics`.
- The agent's `Outcome` isn't `Complete`: `CoWriteError::AgentOutcome`,
  the same six-variant handling (`StepLimit`, `VerificationFailed`,
  `Cancelled`, `RepeatedAction`, `Blocked`, `Error`) validate and
  investigate already use.

## Testing

- `Store::latest_checkpoint_time`: unit tests in `zorp-track`, covering
  no-checkpoint-yet (`None`), one checkpoint, and multiple checkpoints of
  different kinds for the same track (only the matching `kind` counts).
- Track-killed and no-metrics gates: unit tests in `zorp-agent` against a
  `Project`/`Store` in a tempdir, no agent involved (checked before the
  agent is built).
- End-to-end: an integration test following `investigate_integration.rs`'s
  shape, a stub `Model` returning fixed prose as the "draft," no MCP
  server needed. Covers: the full round trip (metric recorded via a
  fixture experiment, `co_write::run` called, `draft.md` written and
  contains the stub's content, checkpoint approved); a rejected
  checkpoint leaving the track's status unchanged (not `Killed`); the
  mtime-warning path (write `draft.md`, touch its mtime forward, call
  `co_write::run` again, confirm it still overwrites and the warning
  doesn't block).

## Out of scope

- Post-hoc numeric claim-checking against the drafted prose (see
  "Grounding the draft, not checking it afterward" above).
- Tamper-evidence hashing of `draft.md`; the mtime check is a warning
  only, not enforced integrity like `prereg.md`'s SHA-256.
- Venue or format matching, and any notion of the draft being "finished"
  or ready to publish; that is `deliver`'s job, not co-write's.
- Multiple draft versions or a history of prior drafts; each call
  overwrites `draft.md` in place (with the mtime warning above), no
  versioning.
